# Beer2beer - Projektregeln und Coding Guidelines
# Clean Architecture - ASP.NET Core 8 Web API

## Architektur-Prinzipien

### Schichtenstruktur (Clean Architecture)
- **Beer2beer.API**: Präsentationsschicht - nur Controllers, Middleware, Extensions, DI-Registrierung
- **Beer2beer.Core**: Dominbschicht - Entities, Interfaces, Services, Mapper, Exceptions
- **Beer2beer.Infrastructure**: Datenzugriffsschicht - DbContext, Repositories, Migrations
- **Beer2beer.UnitTest**: Testprojekt für Unit Tests

### Abhängigkeitsregeln
- API hängt von Core und Infrastructure ab
- Infrastructure hängt von Core ab
- Core hängt von keinen anderen Projekten ab (rein)
- Jede Schicht darf nur von unteren Schichten abhängen, niemals umgekehrt

---

## Datei- und Ordnerstruktur

### Entity-Regeln (Core/Entities/)
- Jede Entity erbt von `Base<T>` für gemeinsame Eigenschaften (Id, EntryDate, UpdateDate)
- Entities werden mit `[Table("TableName")]` annotiert
- ViewModels werden in gleichen Ordner wie Entities gespeichert
- Naming: Entity = `Customer`, ViewModel = `CustomerViewModel`

### Interface-Regeln (Core/Interfaces/)
- Interfaces beginnen mit `I` (z.B. `ICustomerRepository`, `ICustomerService`)
- Repository-Interfaces erben von `IBaseRepository<T>`
- Service-Interfaces sind eigenständig pro Domäne
- `IBaseMapper<TSource, TDestination>` für Mapping-Interfaces

### Repository-Regeln (Infrastructure/Repositories/)
- Repository-Klassen erben von `BaseRepository<T>`
- Repository-Interfaces sind in Core/Interfaces definiert
- Naming: `ICustomerRepository` (Core) → `CustomerRepository` (Infrastructure)
- Nur Datenzugriff, keine Business Logic

### Service-Regeln (Core/Services/)
- Services sind in Core/Services definiert
- Services implementieren Interfaces aus Core/Interfaces
- Business Logic gehört hierher, nicht in Repositories
- Mapping zwischen Entity und ViewModel über IBaseMapper

### Controller-Regeln (API/Controllers/)
- Controllers erben von `ControllerBase`
- Routing: `[Route("api/[controller]")]` + `[ApiController]`
- Dependency Injection über Konstruktor
- Logging über `ILogger<T>`
- Exception-Handling mit try/catch und angemessenen HTTP-Statuscodes
- Keine Business Logic in Controllers - nur Aufruf von Services

---

## Naming Conventions

### Allgemein
- PascalCase für Klassen, Methoden, Properties
- camelCase für lokale Variablen, Parameter
- Interfaces beginnen mit `I`
- Private Felder mit `_` Prefix (z.B. `_customerRepository`)
- Methoden beginnen mit Verb (z.B. `GetCustomers`, `CreateCustomer`)

### Dateien
- Eine Klasse pro Datei
- Dateiname = Klassenname (z.B. `CustomerController.cs` für `CustomerController`)
- ViewModels mit `ViewModel` Suffix

---

## DI-Registrierung (API/Extensions/ServiceExtension.cs)

### Service-Lebenszyklen
- **Services**: `AddScoped<ICustomerService, CustomerService>()` (pro Request)
- **Repositories**: `AddTransient<ICustomerRepository, CustomerRepository()`` (neue Instanz pro Aufruf)
- **Mapper**: `AddSingleton<IBaseMapper<...>>(...)` (eine Instanz pro App)

### Mapping-Konfiguration
- AutoMapper-Konfiguration in ServiceExtension.cs
- Bidirektionales Mapping: Entity ↔ ViewModel
- Für jede Domäne zwei Maps erstellen

---

## Datenbank-Regeln (Infrastructure/Data/)

### DbContext
- `ApplicationDbContext` erbt von `IdentityDbContext`
- DbSet-Properties für jede Entity (z.B. `DbSet<Customer> Customers`)
- Konfiguration über `OnModelCreating`
- Seed-Daten in `ApplicationDbContextConfigurations.SeedData`

### Migrations
- Nur über EF Core CLI oder Package Manager Console
- Migration-Dateien in Infrastructure/Migrations speichern
- Vor Migrations: Sicherstellen, dass DbContext korrekt konfiguriert ist

---

## Exception-Handling

### Custom Exceptions
- Custom Exceptions in Core/Exceptions/
- `NotFoundException` für nicht gefundene Daten
- Exceptions mit angemessenen Nachrichten werfen
- In Controllers: Exceptions abfangen und passende HTTP-Statuscodes zurückgeben

### Controller-Fehlerbehandlung
- 400 Bad Request für Validierungsfehler
- 404 Not Found für nicht existierende Ressourcen
- 500 Internal Server Error für unerwartete Exception
- Logging aller Exception mit ILogger

---

## Validierung

### Entity-Validierung
- Data Annotations auf Entities (z.B. `[Required]`, `[StringLength]`)
- ViewModels mit gleichen Validierungsregeln

### Controller-Validierung
- `ModelState.IsValid` vor dem Verarbeiten prüfen
- Bei ungültigem ModelState: 400 Bad Request zurückgeben

---

## Logging

### Middleware
- Request/Response Logging über `RequestResponseLoggingMiddleware`
- Logging von HTTP-Methode, Path und Statuscodes

### Controller-Logging
- ILogger<T> in Constructor injecten
- Error-Logging bei Exception mit `logger.LogError(ex, message)`

---

## Test-Struktur (Beer2beer.UnitTest/)

### Organisation
- Testdateien in API/Ordner
- Eine Testklasse pro Controller/Service
- Testmethoden mit Klarem, beschreibendem Namen

### Frameworks
- xUnit als Test-Framework
- Moq für Mocking von Abhängigkeiten
- FluentAssertions für aussagekräftige Assertions

---

## Code-Qualität

### Generelle Regeln
- Keine auskommentierten Codeblöcke (nur wenn als Platzhalter gekennzeichnet)
- Keine unused using statements
- Moderne C# Features verwenden (z.B. null-conditional operator)
- Async/Attent für alle I/O-Operationen

### Documentation
- XML-Kommentare für public Members (optional)
- Klare, aussagekräftige Variablennamen
- Komplexe Logik durch benannte Methoden entzerren

---

## Git-Regeln

### Commit-Messages
- Klare, beschreibende Messages
- Immer Bezug zum geänderten Feature/Bugfix

### Branches
- Feature-Branches für neue Features
- Hotfix-Branches für kritische Fixes
- Develop als Integrationsbranch

## Erweiterungsrichtlinien

### Neue Domäne hinzufügen (z.B. Product)
1. Entity in Core/Entities/ erstellen (erbt von Base<T>)
2. ViewModel in Core/Entities/ erstellen
3. Interface IProductRepository in Core/Interfaces/ erstellen
4. Interface IProductService in Core/Interfaces/ erstellen
5. Repository in Infrastructure/Repositories/ implementieren
6. Service in Core/Services/ implementieren
7. Controller in API/Controllers/ erstellen
8. AutoMapper-Konfiguration in ServiceExtension.cs erweitern
9. DI-Registrierung in ServiceExtension.cs hinzufügen
10. DbSet in ApplicationDbContext hinzufügen
11. Migration erstellen

---

## Bekannte Einschränkungen
- SQLite als Datenbank (für Development)
- Kein Authentication/Authorization implementiert (nur Identity DbContext)
- Einige Services haben nicht implementierte Methoden (z.B. AppUserService)
- Performance-Testing mit BenchmarkDotNet vorbereitet aber nicht aktiv
